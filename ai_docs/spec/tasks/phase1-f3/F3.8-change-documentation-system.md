## 4. Background: AI-Optimized Documentation

### 4.1 Why Semantic Naming Matters

Traditional chronological naming (e.g., `CHG-2025-01-09-001.md`) is human-centric. An AI agent benefits from:

| Approach | AI Benefit |
|----------|------------|
| **Resource-first naming** | Glob patterns find related changes (`*living-room-tv*`) |
| **Semantic filenames** | Filename alone communicates content |
| **Structured index** | Programmatic queries without reading all files |
| **No dates in paths** | Temporal data in metadata, not identity |

### 4.2 Documentation as First-Class Requirement

Every infrastructure modification must be documented because:
1. **Context for future operations** - Claude can reference past decisions
2. **Audit trail** - What was done, why, and how to undo
3. **Pattern learning** - Similar operations can reference past examples
4. **Rollback support** - Links changes to rollback IDs

### 4.3 Documentation vs Audit Logging

| Aspect | Audit Log (F2.8) | Change Documentation (F3.8) |
|--------|------------------|----------------------------|
| **Format** | Structured JSON | Semantic Markdown |
| **Content** | What happened | Why it happened + context |
| **Created by** | Automatic (hook) | Claude (guided by pattern) |
| **Purpose** | Technical record | Knowledge for future queries |
| **Queryable by** | Parsing tools | Glob/Grep + Index |

### 5.2 Naming Convention

**Pattern:** `{primary-resource}-{operation}.md`

| Component | Description | Examples |
|-----------|-------------|----------|
| `primary-resource` | Main affected resource (slugified) | `living-room-tv`, `iot-media-vlan`, `camera-network` |
| `operation` | What was done | `isolation`, `creation`, `firewall-setup`, `blocking` |

**Examples:**
- `living-room-tv-isolation.md`
- `iot-media-vlan-creation.md`
- `camera-network-firewall-setup.md`
- `guest-wifi-24h-creation.md`
- `unknown-device-aa11bb22-blocking.md`

**Rules:**
- Lowercase with hyphens (no spaces, underscores, or special chars)
- Resource name first (what was affected)
- Operation second (what was done)
- No dates in filename (dates in metadata)
- Keep names concise but descriptive

### 5.5 Post-Change Documentation Hook

**File: `.claude/hooks/post-change-document.sh`**

This hook triggers after configuration changes and reminds Claude to create documentation.

```bash
#!/usr/bin/env bash
#
# Post-change documentation reminder hook
# Triggers after configuration changes to prompt documentation workflow
#
# This hook does NOT block - it outputs a reminder message
#

set -euo pipefail

# Read input
INPUT=$(cat)

# Parse JSON
TOOL_NAME=$(echo "$INPUT" | jq -r '.tool_name // "unknown"')
SUCCESS=$(echo "$INPUT" | jq -r '.tool_response.success // false')
ROLLBACK_ID=$(echo "$INPUT" | jq -r '.tool_response.rollback_id // "none"')

# Only prompt for successful configuration changes
if [[ "$SUCCESS" != "true" ]]; then
    exit 0
fi

# Extract operation type from tool name
OPERATION=""
case "$TOOL_NAME" in
    *create_network*)
        OPERATION="network creation"
        ;;
    *delete_network*)
        OPERATION="network deletion"
        ;;
    *create_firewall_rule*)
        OPERATION="firewall rule creation"
        ;;
    *delete_firewall_rule*)
        OPERATION="firewall rule deletion"
        ;;
    *set_port_vlan*)
        OPERATION="port VLAN configuration"
        ;;
    *block_client*)
        OPERATION="client blocking"
        ;;
    *unblock_client*)
        OPERATION="client unblocking"
        ;;
    *)
        # Not a tracked configuration change
        exit 0
        ;;
esac

# Output documentation reminder
cat << EOF

---
📋 **DOCUMENTATION REQUIRED**

A $OPERATION has been completed successfully.
Rollback ID: $ROLLBACK_ID

Before this task can be considered complete, you must:

1. Create a change document in \`ai_docs/changes/docs/\`
   - Use semantic naming: \`{resource}-{operation}.md\`
   - Follow template: \`ai_docs/changes/templates/change-doc.md\`

2. Update the index: \`ai_docs/changes/index.yaml\`
   - Add entry to \`changes\` list
   - Update \`by_resource\`, \`by_type\`, \`by_tag\` sections
   - Add to \`recent\` list

This documentation requirement is MANDATORY per project safety rules.
---

EOF
```

## 12. Documentation Contract

This section establishes the binding contract for documentation artifacts. Documentation is not optional commentary—it is a **mandatory output** of task execution that determines task success or failure.

### 12.1 Contract Principles

| Principle | Requirement |
|-----------|-------------|
| **Mandatory Output** | Documentation artifacts are required outputs of any task that modifies infrastructure |
| **Schema-Validated** | All documentation must conform to the typed block schema defined below |
| **Machine-Verifiable** | Documentation validity is mechanically checkable, not subjectively judged |
| **Failure Condition** | A task is considered **FAILED** if documentation is not emitted, regardless of whether the infrastructure change itself succeeded |

**Critical Rule:** An infrastructure change that succeeds but lacks proper documentation is a **failed task**. The system state is now undocumented, which is worse than a failed change that was never applied.

### 12.2 Typed Documentation Block Schema

All change documentation artifacts must contain the following typed blocks. Each block has defined ownership (which skills may write to it) and lifecycle phase constraints.

#### 12.2.1 Block Definitions

| Block | Required | Description |
|-------|----------|-------------|
| `intent` | Yes | The user's goal and the interpreted objective |
| `observation` | Yes | Discovered state before changes were made |
| `reasoning` | Yes | Why this approach was chosen over alternatives |
| `assumptions_and_unknowns` | Yes | Unverified claims, inferred values, incomplete data |
| `rollback` | Yes | Complete reversal procedure with rollback IDs |
| `changes` | Yes | What was modified, created, or deleted |
| `verification` | Yes | How success was confirmed |

#### 12.2.2 Block Schema

```yaml
# Documentation Block Schema v1.0
# All blocks are REQUIRED unless explicitly marked optional

schema_version: "1.0"

blocks:
  intent:
    required: true
    description: "User's stated goal and Claude's interpretation"
    fields:
      - user_request: string (required)      # Original user request verbatim
      - interpreted_goal: string (required)  # Claude's understanding
      - success_criteria: list[string]       # How success is measured
    writable_by:
      - skill: "planning"
        phases: [pre_execution]
    append_only: true

  observation:
    required: true
    description: "Discovered infrastructure state before changes"
    fields:
      - timestamp: datetime (required)
      - resources_examined: list[resource]
      - current_state: object (required)
      - relevant_context: string
    writable_by:
      - skill: "discovery"
        phases: [pre_execution]
      - skill: "verification"
        phases: [post_execution]
    append_only: true

  reasoning:
    required: true
    description: "Justification for chosen approach"
    fields:
      - chosen_approach: string (required)
      - alternatives_considered: list[alternative]
      - rejection_reasons: list[string]
      - constraints_applied: list[string]
      - safety_considerations: list[string]
    writable_by:
      - skill: "planning"
        phases: [pre_execution]
    append_only: true

  assumptions_and_unknowns:
    required: true
    description: "Registry of unverified information"
    fields:
      - assumptions: list[assumption] (required)
      - unknowns: list[unknown] (required)
      - inferred_defaults: list[inference]
      - unverified_claims: list[claim]
    writable_by:
      - skill: "planning"
        phases: [pre_execution]
      - skill: "execution"
        phases: [during_execution]
      - skill: "verification"
        phases: [post_execution]
    append_only: true
    validation:
      - rule: "non_empty_when_assumptions_exist"
        description: "If any inference or assumption was made, this block must not be empty"

  rollback:
    required: true
    description: "Complete reversal procedure"
    fields:
      - rollback_ids: list[string] (required)
      - reversal_order: list[step] (required)
      - dependencies: list[string]
      - time_sensitivity: string
      - expiry: datetime
      - manual_steps: list[string]
    writable_by:
      - skill: "execution"
        phases: [during_execution, post_execution]
    append_only: true
    validation:
      - rule: "must_have_rollback_ids"
        description: "At least one rollback_id required for any state-changing operation"

  changes:
    required: true
    description: "Record of what was modified"
    fields:
      - operations: list[operation] (required)
      - resources_affected: list[resource] (required)
      - before_state: object
      - after_state: object (required)
    writable_by:
      - skill: "execution"
        phases: [during_execution, post_execution]
    append_only: true

  verification:
    required: true
    description: "Confirmation of success"
    fields:
      - method: string (required)
      - timestamp: datetime (required)
      - result: enum[success, partial, failed] (required)
      - evidence: list[string]
      - discrepancies: list[string]
    writable_by:
      - skill: "verification"
        phases: [post_execution]
    append_only: true
```

#### 12.2.3 Lifecycle Phases

| Phase | Description | Allowed Operations |
|-------|-------------|-------------------|
| `pre_execution` | Before any infrastructure changes | Write to: intent, observation, reasoning, assumptions_and_unknowns |
| `during_execution` | While changes are being applied | Write to: assumptions_and_unknowns, rollback, changes |
| `post_execution` | After changes complete | Write to: observation, assumptions_and_unknowns, rollback, changes, verification |

### 12.3 Assumptions and Unknowns Register

The `assumptions_and_unknowns` block is a **mandatory registry** that must be populated whenever Claude:

1. **Infers a default value** not explicitly stated by the user
2. **Relies on vendor documentation** that cannot be verified at runtime
3. **Makes observations that are incomplete** (e.g., cannot verify all paths)
4. **Assumes behavior** based on pattern matching from similar systems

#### 12.3.1 Register Entry Types

```yaml
assumption:
  statement: string        # What is being assumed
  basis: string           # Why this assumption was made
  risk_if_wrong: string   # Consequence if assumption is false
  verification_method: string  # How to verify (if possible)

unknown:
  description: string     # What is not known
  impact: string          # How this affects the operation
  mitigation: string      # How risk is being managed

inference:
  value: string           # The inferred value
  source: string          # Where it came from (default, similar system, etc.)
  confidence: enum[high, medium, low]

claim:
  statement: string       # The unverified claim
  source: string          # Vendor docs, user statement, etc.
  verified: boolean       # Always false in this register
```

#### 12.3.2 Spec Violation Conditions

The following conditions constitute a **specification violation**:

| Condition | Violation |
|-----------|-----------|
| Assumption made but register empty | VIOLATION: Missing assumptions documentation |
| Default value inferred but not recorded | VIOLATION: Undocumented inference |
| Vendor behavior assumed but not noted | VIOLATION: Unrecorded vendor assumption |
| Register present but `assumptions` list empty when inferences were made | VIOLATION: Incomplete register |

### 12.4 Reversibility Requirement

**Execution Gate:** No infrastructure modification may proceed unless a valid rollback block can be generated.

#### 12.4.1 Rollback Block Requirements

Before executing any state-changing operation, the system must:

1. **Confirm rollback capability exists** - The target system supports undo (rollback_id will be returned)
2. **Pre-generate rollback procedure** - Document how to reverse before applying
3. **Validate rollback completeness** - All affected resources have reversal paths

#### 12.4.2 Execution Authorization Matrix

| Rollback Block Status | Human Approval | Execution Allowed |
|----------------------|----------------|-------------------|
| Successfully generated | Not required | ✅ YES |
| Successfully generated | Provided | ✅ YES |
| Generation failed | Not provided | ❌ NO |
| Generation failed | Elevated approval artifact present | ✅ YES (with explicit risk acknowledgment) |
| Partial generation | Not provided | ❌ NO |
| Partial generation | Elevated approval for missing parts | ✅ YES (with explicit risk acknowledgment) |

#### 12.4.3 Elevated Approval Artifact

When rollback cannot be guaranteed, execution requires an **elevated approval artifact**:

```yaml
elevated_approval:
  timestamp: datetime
  approver: "user"
  risk_acknowledged:
    - description: "Rollback may not be possible for {operation}"
    - affected_resources: list[resource]
    - manual_recovery_required: boolean
  approval_statement: string  # User's explicit acknowledgment
```

### 12.5 Append-Only Lifecycle Rules

Documentation artifacts are **immutable once written**. This ensures complete audit trails and prevents retroactive modification of records.

#### 12.5.1 Core Rules

| Rule | Description |
|------|-------------|
| **No Overwrites** | Skills may not overwrite existing documentation artifacts |
| **No Deletions** | Documentation artifacts may not be deleted |
| **No In-Place Edits** | Existing blocks may not be modified after initial write |
| **Append Only** | New information is appended, never replaces |

#### 12.5.2 Correction Procedure

When a correction or update is needed:

1. **Create a new documentation artifact** with type `correction` or `amendment`
2. **Reference the original artifact** by ID
3. **Describe the delta** - what was wrong and what the correction is
4. **Preserve the original** - do not modify it

```yaml
# Correction artifact structure
correction:
  id: "{original-id}-correction-{sequence}"
  references:
    original_artifact: "{original-id}"
    original_timestamp: datetime
  correction_type: enum[factual_error, incomplete_info, superseded, clarification]
  delta:
    field_corrected: string
    original_value: any
    corrected_value: any
    reason: string
  timestamp: datetime
  created_by: string
```

#### 12.5.3 Amendment Chain

Multiple corrections create an amendment chain:

```
living-room-tv-isolation.md (original)
  └── living-room-tv-isolation-correction-001.md
        └── living-room-tv-isolation-correction-002.md
```

The index must track the full chain and point to the **current authoritative version** (latest in chain).

### 12.6 Validation Requirements

Documentation artifacts must be **mechanically verifiable**. The documentation skill must enforce validation and **fail the task** if validation fails.

#### 12.6.1 Three-Question Rule

Every documentation artifact must mechanically answer three questions:

| Question | Answered By Block | Validation Check |
|----------|-------------------|------------------|
| **What changed?** | `changes` block | `changes.operations` is non-empty AND `changes.resources_affected` is non-empty |
| **Why did it change?** | `intent` + `reasoning` blocks | `intent.interpreted_goal` is non-empty AND `reasoning.chosen_approach` is non-empty |
| **How to undo it?** | `rollback` block | `rollback.rollback_ids` is non-empty AND `rollback.reversal_order` is non-empty |

#### 12.6.2 Validation Procedure

```python
def validate_documentation(artifact: DocumentationArtifact) -> ValidationResult:
    """
    Validate documentation artifact against contract requirements.
    Returns failure if any required element is missing.
    """
    errors = []

    # Three-question validation
    if not artifact.changes.operations:
        errors.append("WHAT_CHANGED: changes.operations is empty")
    if not artifact.changes.resources_affected:
        errors.append("WHAT_CHANGED: changes.resources_affected is empty")

    if not artifact.intent.interpreted_goal:
        errors.append("WHY_CHANGED: intent.interpreted_goal is empty")
    if not artifact.reasoning.chosen_approach:
        errors.append("WHY_CHANGED: reasoning.chosen_approach is empty")

    if not artifact.rollback.rollback_ids:
        errors.append("HOW_TO_UNDO: rollback.rollback_ids is empty")
    if not artifact.rollback.reversal_order:
        errors.append("HOW_TO_UNDO: rollback.reversal_order is empty")

    # Required blocks validation
    for block_name in REQUIRED_BLOCKS:
        if not hasattr(artifact, block_name) or getattr(artifact, block_name) is None:
            errors.append(f"MISSING_BLOCK: {block_name} is required")

    # Assumptions register validation
    if artifact.has_inferences() and not artifact.assumptions_and_unknowns.assumptions:
        errors.append("ASSUMPTIONS: Register empty but inferences were made")

    return ValidationResult(
        valid=len(errors) == 0,
        errors=errors,
        task_status="FAILED" if errors else "PASSED"
    )
```

#### 12.6.3 Validation Failure Consequences

| Validation Result | Task Status | Required Action |
|-------------------|-------------|-----------------|
| All checks pass | COMPLETED | None |
| Any check fails | FAILED | Task cannot be marked complete |
| Partial checks pass | FAILED | Missing elements must be added |

**Enforcement:** The documentation skill must run validation before reporting task completion. If validation fails, the skill must:

1. Report which checks failed
2. Attempt to gather missing information
3. Re-validate after additions
4. Only report success when all validations pass
