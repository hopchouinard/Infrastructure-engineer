## 4. Background: Claude Code Extensibility

### 4.1 Native Skill System

Claude Code provides a native skill system that differs from the original F3 spec. Key points:

| Component | Location | Format | Activation |
|-----------|----------|--------|------------|
| **Skills** | `.claude/skills/name/SKILL.md` | YAML frontmatter + Markdown | Automatic (context-matching) |
| **Slash Commands** | `.claude/commands/name.md` | YAML frontmatter + Markdown | Manual (`/name [args]`) |
| **Hooks** | `.claude/settings.json` | JSON | Event-driven |
| **CLAUDE.md** | Project root | Markdown | Always loaded |

### 4.2 Skills vs Custom Engine

The original F3 feature spec described a custom Python skill engine. However, Claude Code's native system makes this unnecessary:

- **Skills** are markdown instruction files that teach Claude how to orchestrate MCP tools
- **Slash Commands** trigger specific workflows when invoked manually
- **Hooks** run scripts on specific events (tool calls, completions)
- Claude handles the orchestration - no custom engine needed

### 4.3 MCP Integration

Skills and commands can invoke F2's MCP tools (e.g., `unifi_list_networks`, `unifi_create_vlan`) directly. Claude sees these tools in its available tools list and follows skill instructions to use them appropriately.

```markdown
# UniFi Infrastructure Management Skill

You are an expert network administrator managing a UniFi-based homelab network.

## Available MCP Tools

You have access to the UniFi MCP server which provides these tools:

### Query Tools (Auto-approved, safe to use freely)
- `unifi_list_networks` - List all VLANs/networks
- `unifi_get_network(identifier)` - Get network by name, ID, or VLAN
- `unifi_list_clients` - List all connected clients
- `unifi_get_client(identifier)` - Get client by name, MAC, or IP
- `unifi_search_clients(pattern)` - Search clients
- `unifi_list_devices` - List switches, APs, gateways
- `unifi_get_device(identifier)` - Get device details
- `unifi_get_port_status(switch, port)` - Get port status
- `unifi_list_firewall_rules` - List all firewall rules

### Configuration Tools (Always confirm with user first)
- `unifi_create_network(name, vlan_id, subnet, ...)` - Create VLAN
- `unifi_update_network(identifier, ...)` - Update network
- `unifi_delete_network(identifier)` - Delete network
- `unifi_create_firewall_rule(name, ruleset, action, ...)` - Create rule
- `unifi_delete_firewall_rule(identifier)` - Delete rule
- `unifi_block_client(mac)` - Block client
- `unifi_unblock_client(mac)` - Unblock client
- `unifi_set_port_vlan(switch, port, vlan_id)` - Set port VLAN

## Workflow Patterns

### Before Any Configuration Change

1. **Gather information** using query tools
2. **Identify affected resources** (devices, clients, rules)
3. **Present a clear change plan** to the user:
   - What will be created/modified/deleted
   - Risk level (LOW/MEDIUM/HIGH)
   - Which devices may be affected
   - Rollback availability
4. **Wait for explicit user confirmation**
5. **Execute with dry_run=true first** if available
6. **Execute the actual change**
7. **Report the result** including any rollback IDs

### Device Isolation Pattern

When user wants to isolate a device:
1. Find the device with `unifi_get_client`
2. List existing networks with `unifi_list_networks`
3. Determine if wired (has switch_mac/switch_port) or wireless
4. Calculate appropriate VLAN ID and subnet
5. Present plan: new VLAN, port change (if wired), firewall rules
6. After confirmation: create VLAN, configure port, create rules
7. Report completion with rollback instructions

### Finding Device Connections

When user asks where a device is connected:
1. Find the device with `unifi_get_client`
2. If wired: report switch name and port number
3. If wireless: report AP name and signal strength
4. Provide additional context (IP, VLAN, uptime)

## Safety Rules

1. **NEVER delete the default network**
2. **NEVER delete a network with active clients** without explicit confirmation
3. **NEVER create "allow any to any" firewall rules**
4. **ALWAYS use descriptive names** for VLANs and rules
5. **ALWAYS report rollback IDs** so changes can be undone
```

### 5.6 Post-Change Hook Script

**File: `.claude/hooks/post-change-log.sh`**

```bash
#!/usr/bin/env bash
# Post-change logging hook for UniFi configuration changes
# Logs all configuration changes to JSON file for audit trail

set -euo pipefail

# Configuration
LOG_DIR="${CLAUDE_PROJECT_DIR:-.}/.claude/logs"
LOG_FILE="$LOG_DIR/infrastructure-changes.json"

# Ensure log directory exists
mkdir -p "$LOG_DIR"

# Read tool input from stdin
INPUT=$(cat)

# Check for jq
if ! command -v jq &> /dev/null; then
    echo "Warning: jq not installed, logging disabled"
    exit 0
fi

# Extract tool data
TOOL_NAME=$(echo "$INPUT" | jq -r '.tool_name // "unknown"')
SUCCESS=$(echo "$INPUT" | jq -r '.result.success // "unknown"')
ROLLBACK_ID=$(echo "$INPUT" | jq -r '.result.rollback_id // "none"')
TOOL_INPUT=$(echo "$INPUT" | jq -c '.tool_input // {}')

# Get timestamp
TIMESTAMP=$(date -u +"%Y-%m-%dT%H:%M:%SZ")

# Create JSON log entry
LOG_ENTRY=$(jq -nc \
    --arg ts "$TIMESTAMP" \
    --arg tool "$TOOL_NAME" \
    --arg success "$SUCCESS" \
    --arg rollback "$ROLLBACK_ID" \
    --argjson input "$TOOL_INPUT" \
    '{
        timestamp: $ts,
        tool: $tool,
        success: $success,
        rollback_id: $rollback,
        input: $input
    }')

# Append to log (JSON Lines format)
echo "$LOG_ENTRY" >> "$LOG_FILE"

# Output for Claude to see
if [[ "$SUCCESS" == "true" ]]; then
    if [[ "$ROLLBACK_ID" != "none" && "$ROLLBACK_ID" != "null" ]]; then
        echo "📝 Change logged. Rollback ID: $ROLLBACK_ID (valid 60 min)"
    else
        echo "📝 Change logged."
    fi
else
    echo "📝 Failed operation logged."
fi
```

- `mcp__unifi__unifi_list_networks` (full path)
- `unifi_list_networks` (short name)

The skill and command files reference tools by their logical names.
