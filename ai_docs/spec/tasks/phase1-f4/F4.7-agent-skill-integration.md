# Task F4.7: Agent-to-Skill Integration

**Phase:** 1 (UniFi Infrastructure)
**Feature:** 4 (SubAgent Integration)
**Milestone:** F4.7 - Agent-to-Skill Integration
**Status:** Not Started

---

## 1. Objective

Define and implement the integration layer between SubAgents (F4) and Skills/Commands (F3), enabling agents to invoke read-only skills for investigation while maintaining the strict read-only constraint for agents.

## 2. Prerequisites

- F4.1-F4.6 completed - all agents defined
- F3 (Claude Code Integration) completed - skills and commands functional
- F2 (UniFi MCP Server) functional - tools available

## 3. Scope

### In Scope

- Define read-only skill/command whitelist for agents
- Document invocation patterns for agents calling skills
- Create integration guidelines
- Test agent→skill invocation
- Ensure permission boundaries are maintained

### Out of Scope

- Modifying F3 skills/commands
- Creating new skills for agent use
- Agent-to-agent communication

---

## 4. Background

### 4.1 Integration Need

SubAgents need to leverage F3 skills/commands for investigation, but must respect the read-only constraint. This integration defines:

- Which skills/commands agents CAN invoke
- How agents invoke them
- What agents do with results

### 4.2 Current State

F3 provides these relevant read-only commands:
- `/infra-find` - Locate device connection point
- `/infra-status` - Network overview
- `/infra-unknown` - List unnamed clients
- `/security-audit` - Security audit (quick mode, without --deep flag)

F3 provides these modifying commands (off-limits to agents):
- `/infra-isolate` - Create VLAN and isolate device
- `/infra-block` / `/infra-unblock` - Block/unblock clients
- `/infra-guest` - Create guest network
- `/infra-undo` - Rollback changes

## Allowed Commands

### /infra-find

**Purpose:** Locate where a device is physically connected

**Agent Use Cases:**
- Troubleshooter: Identify connection point for problem device
- Design Advisor: Understand physical topology
- Change Planner: Inventory affected switch ports

**Invocation Pattern:**
```
When investigating a specific device:
1. First try: unifi_get_client(identifier)
2. If more detail needed: /infra-find [device]
3. Parse results for switch/AP, port, signal info
```

**Example:**
```
Agent: "To understand where this device is connected, let me find its
physical connection point."

[Invokes /infra-find "Samsung TV"]

Results inform diagnosis or planning.
```

### /infra-status

**Purpose:** Get network-wide overview

**Agent Use Cases:**
- Design Advisor: Understand current network topology
- Security Audit: Get complete network picture
- Change Planner: Inventory all resources

**Invocation Pattern:**
```
When starting broad analysis:
1. /infra-status → Get overview
2. Drill down with specific queries as needed
```

**Example:**
```
Agent: "Let me get an overview of your current network configuration."

[Invokes /infra-status]

Results provide context for analysis.
```

### /infra-unknown

**Purpose:** List unnamed/unknown clients

**Agent Use Cases:**
- Security Audit: Identify unknown devices
- Design Advisor: Understand device inventory
- Troubleshooter: Find unidentified devices

**Invocation Pattern:**
```
When analyzing client security:
1. /infra-unknown → Get list of unnamed clients
2. Analyze distribution by network
3. Flag concerning patterns
```

### /security-audit (quick mode)

**Purpose:** Quick security check (without --deep flag, not the SubAgent)

**Agent Use Cases:**
- Security Deep Audit: Supplement SubAgent analysis with quick command output
- Troubleshooter: Quick security context during diagnosis
- Design Advisor: Understand security posture before design

**Invocation Pattern:**
```
When security context needed:
1. /security-audit → Quick checks (NOT --deep, which launches SubAgent)
2. Agent incorporates findings into analysis
```

**Note:** Agents should NOT use `--deep` flag as that would recursively launch another SubAgent.

## Prohibited Commands

Agents MUST NOT invoke these commands:

| Command | Why Prohibited |
|---------|---------------|
| `/infra-isolate` | Creates networks, modifies ports |
| `/infra-block` | Blocks clients |
| `/infra-unblock` | Unblocks clients |
| `/infra-guest` | Creates guest network |
| `/infra-undo` | Modifies configuration |
| `/infra-rename` | Modifies client name |

Instead of invoking these, agents MUST:
1. Recommend the action
2. Include the command in the Execution Plan
3. Let the user execute it

## Invocation Guidelines

### When to Use Skills vs Direct Tools

| Scenario | Use Skill/Command | Use Direct MCP Tool |
|----------|-------------------|---------------------|
| Simple data query | No | Yes (`unifi_get_*`) |
| Complex formatted output | Yes (`/infra-find`) | No |
| Broad overview | Yes (`/infra-status`) | No |
| Specific attribute | No | Yes |
| Already in agent context | No (continue with tools) | Yes |

### Invocation Flow

```
1. Agent receives user request
2. Agent determines what data is needed
3. For simple queries: Use MCP tools directly
4. For complex queries: Invoke read-only command
5. Parse results into agent's analysis
6. Continue with investigation
```

### Communicating Results

When agent invokes a skill/command:

```markdown
Good Pattern:
"Let me check where that device is connected."
[Invokes /infra-find]
"I found that [device] is connected to [switch:port].
Based on this, [continue analysis]..."

Not Good:
[Silent invocation with no context]
or
"I'm going to invoke the /infra-find command to query..."
[Too verbose about mechanics]
```

## Integration in Agent Definitions

Each agent's AGENT.md uses standard Claude Code frontmatter:

```yaml
---
name: agent-name
description: |
  Agent description with activation triggers...
tools: Read, Grep, Glob
model: sonnet
---
```

The allowed/prohibited commands are documented in the agent's **system prompt body**, not in frontmatter:

```markdown
## Tool & Command Constraints

### Allowed Commands
- `/infra-find`, `/infra-status`

### Prohibited Commands (DO NOT INVOKE)
- `/infra-isolate`, `/infra-block`
```

These are behavioral instructions for the agent, not technical enforcement.

## Enforcement

The read-only boundary is enforced through:

1. **Agent Instructions**: AGENT.md explicitly lists allowed/prohibited
2. **Behavior Training**: Agent knows to recommend, not execute
3. **Settings Permissions**: Can add tool-level restrictions
4. **Review**: Human reviews execution plans before running

## Examples

### Troubleshooter Using /infra-find

```
User: "My laptop keeps disconnecting"

Troubleshooter:
1. unifi_get_client("laptop") → Basic info
2. /infra-find "laptop" → Detailed connection info
3. Analyze: Signal -72 dBm, connected to far AP
4. Diagnose: Weak signal is likely cause
5. Recommend: Move closer to AP or improve coverage
```

### Design Advisor Using /infra-status

```
User: "Help me design a camera network"

Design Advisor:
1. /infra-status → Current topology
2. Parse: 3 VLANs exist, VLAN IDs 1, 20, 50 in use
3. Analyze: ID range 60-69 available for security
4. Design: Recommend VLAN 60 "Cameras"
5. Output: Execution Plan with /infra-isolate commands
```

### Security Audit Using Multiple

```
Security Audit:
1. /infra-status → Network overview
2. /infra-unknown → Unnamed clients
3. /security-audit → Quick checks (NOT --deep)
4. unifi_list_firewall_rules() → Detailed rules
5. Comprehensive analysis combining all sources
6. Output: Detailed audit report
```
