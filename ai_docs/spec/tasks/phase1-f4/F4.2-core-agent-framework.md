## 1. Objective

Define the core framework patterns that all SubAgents share: investigation workflows, reasoning structures, output formats, error handling, and user interaction patterns. This ensures consistency across all agents while allowing domain-specific customization.

## 2. Prerequisites

- F4.1 (Project Setup) completed - directory structure exists
- F3 (Claude Code Integration) functional - skills and commands available
- F2 (UniFi MCP Server) functional - query tools available

## 3. Scope

### In Scope

- Define standard agent lifecycle (invoke → investigate → reason → output)
- Create investigation workflow templates
- Define reasoning and analysis patterns
- Establish output format standards (reports vs execution plans)
- Define error handling and recovery patterns
- Create user interaction guidelines (clarifying questions)
- Document background execution patterns

### Out of Scope

- Individual agent implementations (F4.3-F4.6)
- Testing framework (F4.8)
- Documentation for users (F4.9)

## 4. Background: Agent Reasoning Model

### 4.1 Agent Lifecycle

Every SubAgent follows a standard lifecycle:

```
┌─────────────────────────────────────────────────────────────────┐
│                    SubAgent Lifecycle                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. INVOCATION                                                   │
│     └─→ Parse user request                                       │
│     └─→ Identify task type and scope                            │
│     └─→ Load relevant context files                             │
│                                                                  │
│  2. CLARIFICATION (if needed)                                    │
│     └─→ Identify ambiguities                                     │
│     └─→ Ask focused questions                                    │
│     └─→ Incorporate answers                                      │
│                                                                  │
│  3. INVESTIGATION                                                │
│     └─→ Execute query patterns                                   │
│     └─→ Gather relevant data                                     │
│     └─→ Explore as needed                                        │
│                                                                  │
│  4. ANALYSIS                                                     │
│     └─→ Correlate findings                                       │
│     └─→ Apply domain expertise                                   │
│     └─→ Identify patterns/issues                                 │
│                                                                  │
│  5. SYNTHESIS                                                    │
│     └─→ Formulate conclusions                                    │
│     └─→ Develop recommendations                                  │
│     └─→ Create execution plan (if changes needed)                │
│                                                                  │
│  6. OUTPUT                                                       │
│     └─→ Format according to output-type                          │
│     └─→ Include all required sections                            │
│     └─→ Provide clear next steps                                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 Investigation vs Execution Boundary

Critical distinction all agents must respect:

```
┌───────────────────────────────────────────────────────────────┐
│                                                               │
│  AGENT DOMAIN (Read-Only)          │  USER DOMAIN (Execute)  │
│  ─────────────────────────         │  ─────────────────────  │
│                                    │                         │
│  • Query network state             │  • Create VLANs         │
│  • Analyze configurations          │  • Modify firewall      │
│  • Identify issues                 │  • Block devices        │
│  • Recommend solutions       ───>  │  • Execute changes      │
│  • Generate execution plans        │  • Rollback if needed   │
│                                    │                         │
│  OUTPUT: Plan, Report              │  INPUT: Approved Plan   │
│                                    │                         │
└───────────────────────────────────────────────────────────────┘
```

# SubAgent Base Pattern

All infrastructure SubAgents extend this base pattern.

## Standard Frontmatter Structure

Claude Code SubAgents use YAML frontmatter with these supported fields:

```yaml
---
name: agent-identifier
description: |
  Multi-line description for activation matching.
  Include trigger phrases and use cases.
  Example: "design", "how should I set up", "architecture"
tools: Read, Grep, Glob
model: sonnet
---
```

**Supported Frontmatter Fields:**

| Field | Required | Description |
|-------|----------|-------------|
| `name` | Yes | Identifier using lowercase-hyphens |
| `description` | Yes | When to invoke; supports multi-line with `\|` |
| `tools` | No | Comma-separated allowlist (omit to inherit all) |
| `disallowedTools` | No | Comma-separated denylist |
| `model` | No | `sonnet`, `opus`, `haiku`, or `inherit` |

**Non-Standard Configuration:**

The following should be documented in the agent's system prompt body, NOT in frontmatter:
- Allowed/prohibited commands (behavioral instruction)
- Context files to read (documented as reference)
- Output format expectations (documented in workflow)

## Standard Behaviors

### Starting an Investigation

1. Acknowledge the user's request
2. State what you will investigate
3. If ambiguous, ask 1-2 clarifying questions (max)
4. Begin systematic data gathering

### During Investigation

1. Gather data methodically
2. Share significant findings as you go
3. If unexpected, note it
4. Don't assume - verify

### Concluding Investigation

1. Summarize what you found
2. State your conclusions clearly
3. Provide recommendations
4. If changes needed: produce Execution Plan
5. Offer to explain any aspect in detail

### Handling Uncertainty

When uncertain about findings:
```
"Based on available data, [finding] appears to be the case.
However, I couldn't verify [X] because [reason].
Before proceeding, you may want to confirm [Y]."
```

### Handling Errors

When a query fails:
```
"I encountered an error querying [resource]: [error]
This might indicate [possible cause].
Alternative approach: [what else I can try]"
```

# Investigation Workflow Patterns

Standard workflows for common investigation types.

## Workflow 1: Single Device Investigation

Use when investigating a specific device.

### Steps

```
1. IDENTIFY DEVICE
   └─→ unifi_get_client(identifier)
   └─→ If not found: unifi_search_clients(pattern)
   └─→ Confirm: "Is this the device you mean? [details]"

2. GATHER DEVICE CONTEXT
   └─→ Connection type (wired/wireless)
   └─→ If wired: unifi_get_device(switch_mac), unifi_get_port_status
   └─→ If wireless: unifi_get_device(ap_mac), signal/channel info
   └─→ Current network/VLAN assignment

3. GATHER NETWORK CONTEXT
   └─→ unifi_get_network(device.network)
   └─→ Relevant firewall rules (if investigating connectivity)
   └─→ Other devices on same network (if relevant)

4. ANALYZE
   └─→ Apply domain-specific analysis
   └─→ Correlate findings
   └─→ Identify issues or opportunities

5. OUTPUT
   └─→ Device summary
   └─→ Findings
   └─→ Recommendations or execution plan
```

### Example Data Collection

```
Device: Living Room TV
├── Client Info
│   ├── MAC: aa:bb:cc:dd:ee:ff
│   ├── IP: 192.168.1.45
│   ├── Hostname: samsung-tv
│   └── Last seen: 2 minutes ago
├── Connection
│   ├── Type: Wireless
│   ├── AP: Living Room AP (signal: -58 dBm)
│   ├── Channel: 36 (5GHz)
│   └── TX/RX: 100/50 Mbps
└── Network
    ├── VLAN: Default (1)
    ├── Subnet: 192.168.1.0/24
    └── Purpose: Corporate
```

## Workflow 2: Network-Wide Investigation

Use when analyzing entire network or multiple resources.

### Steps

```
1. GATHER TOPOLOGY
   └─→ unifi_list_networks() → All VLANs
   └─→ unifi_list_devices() → All infrastructure
   └─→ unifi_list_clients(active_only=true) → All clients

2. GATHER CONFIGURATION
   └─→ unifi_list_firewall_rules() → Security config
   └─→ Per-network details as needed

3. CATEGORIZE
   └─→ Group devices by type/network
   └─→ Identify patterns
   └─→ Flag anomalies

4. ANALYZE
   └─→ Apply analysis framework
   └─→ Compare against best practices
   └─→ Identify issues/opportunities

5. OUTPUT
   └─→ Network overview
   └─→ Categorized findings
   └─→ Prioritized recommendations
```

## Workflow 3: Comparative Analysis

Use when comparing current state to desired state.

### Steps

```
1. UNDERSTAND DESIRED STATE
   └─→ Clarify user's goal
   └─→ Document target configuration

2. GATHER CURRENT STATE
   └─→ Use network-wide workflow
   └─→ Focus on relevant resources

3. GAP ANALYSIS
   └─→ Current vs Desired comparison
   └─→ List changes needed
   └─→ Identify dependencies

4. PLAN TRANSFORMATION
   └─→ Order changes by dependency
   └─→ Identify risks
   └─→ Plan rollback strategy

5. OUTPUT
   └─→ Current state summary
   └─→ Desired state description
   └─→ Execution plan for transformation
```

## Workflow 4: Issue Diagnosis

Use when troubleshooting problems.

### Steps

```
1. UNDERSTAND SYMPTOMS
   └─→ What is failing?
   └─→ When did it start?
   └─→ Is it intermittent or constant?
   └─→ What changed recently?

2. GATHER EVIDENCE
   └─→ Affected device(s) status
   └─→ Network path analysis
   └─→ Configuration review
   └─→ Log analysis (if available)

3. HYPOTHESIZE
   └─→ List possible causes
   └─→ Rank by likelihood
   └─→ Identify tests for each hypothesis

4. INVESTIGATE HYPOTHESES
   └─→ Test most likely first
   └─→ Gather supporting/contradicting evidence
   └─→ Narrow down root cause

5. OUTPUT
   └─→ Diagnosis summary
   └─→ Root cause (if identified)
   └─→ Recommended fix
   └─→ Execution plan (if changes needed)
```

# Analysis Frameworks

Standard frameworks for analyzing network configurations.

## Framework 1: Security Analysis

### Checklist Categories

#### 1. Access Control
- [ ] No "allow any to any" rules
- [ ] Guest networks isolated from LAN
- [ ] IoT networks isolated appropriately
- [ ] Management interfaces protected
- [ ] Default passwords changed (if detectable)

#### 2. Network Segmentation
- [ ] Sensitive resources on separate VLANs
- [ ] Inter-VLAN traffic controlled by firewall
- [ ] Guest traffic cannot reach internal resources
- [ ] IoT devices on dedicated network

#### 3. Client Security
- [ ] Unknown devices flagged
- [ ] Critical devices on appropriate networks
- [ ] No unexpected devices on management VLAN
- [ ] Blocked devices list reviewed

#### 4. Rule Hygiene
- [ ] No disabled rules that should be enabled
- [ ] No redundant rules
- [ ] Rules have descriptive names
- [ ] Logging enabled for important rules

### Severity Classification

| Severity | Criteria | Response Time |
|----------|----------|---------------|
| CRITICAL | Immediate security risk, exploit possible | Immediate |
| HIGH | Significant vulnerability, should fix soon | Days |
| MEDIUM | Weakness, fix when convenient | Weeks |
| LOW | Best practice improvement | Optional |
| INFO | Observation, no action required | N/A |

## Framework 2: Design Analysis

### Evaluation Criteria

#### Scalability
- Can the design accommodate growth?
- Are VLAN IDs organized for expansion?
- Is there subnet space for new devices?

#### Maintainability
- Is the naming convention consistent?
- Are configurations documented?
- Is the design easy to understand?

#### Resilience
- Are there single points of failure?
- What happens if a device fails?
- Is redundancy appropriate?

#### Performance
- Are high-bandwidth devices properly placed?
- Is there potential for congestion?
- Are WiFi channels optimized?

### Design Quality Rating

```
EXCELLENT: Follows all best practices, scalable, well-documented
GOOD: Mostly best practices, minor improvements possible
FAIR: Functions but has significant improvement opportunities
POOR: Multiple issues, redesign recommended
CRITICAL: Fundamental problems, immediate attention needed
```

## Framework 3: Change Impact Analysis

### Impact Categories

#### Service Impact
- Which services will be affected?
- Duration of disruption?
- Can users work around it?

#### Device Impact
- Which devices will lose connectivity?
- For how long?
- Will they auto-reconnect?

#### Security Impact
- Does this change exposure?
- Are there temporary vulnerabilities during change?
- Does it improve or reduce security?

#### Rollback Complexity
- Can this be easily undone?
- What's the rollback time?
- Are there dependencies that complicate rollback?

### Risk Matrix

```
                    IMPACT
                    Low    Medium    High
            ┌──────┬──────┬──────┬──────┐
    Low     │  1   │  2   │  3   │
LIKELIHOOD  │──────┼──────┼──────┤
    Medium  │  2   │  4   │  6   │
            │──────┼──────┼──────┤
    High    │  3   │  6   │  9   │
            └──────┴──────┴──────┘

1-2: Low risk, proceed with normal caution
3-4: Medium risk, ensure rollback ready
6+:  High risk, consider staging or maintenance window
```

# Error Handling Patterns

How SubAgents should handle errors and edge cases.

## Query Failures

### MCP Tool Returns Error

```markdown
When: Tool call fails with error

Response Pattern:
"I encountered an error while querying [resource]:
Error: [error message]

This might indicate:
- [Possible cause 1]
- [Possible cause 2]

I'll try an alternative approach: [what you'll do next]
Or if you'd like, you can: [user action that might help]"
```

### Resource Not Found

```markdown
When: Searched resource doesn't exist

Response Pattern:
"I couldn't find a [resource type] matching '[identifier]'.

I searched using:
- [Search method 1]
- [Search method 2]

Similar [resources] I found:
- [Similar 1]
- [Similar 2]

Did you mean one of these? Or please provide more details about [resource]."
```

### Multiple Matches

```markdown
When: Query returns multiple possible matches

Response Pattern:
"I found multiple [resources] that could match '[identifier]':

1. [Match 1] - [distinguishing details]
2. [Match 2] - [distinguishing details]
3. [Match 3] - [distinguishing details]

Which one are you referring to?"
```

## Data Quality Issues

### Incomplete Data

```markdown
When: Retrieved data is missing expected fields

Response Pattern:
"I gathered data on [resource], but some information isn't available:
- Available: [what we have]
- Missing: [what's missing]

This might be because [reason].
I'll proceed with available data, but note that [caveat]."
```

### Stale Data

```markdown
When: Data appears outdated

Response Pattern:
"Note: The data for [resource] may be outdated.
Last updated: [timestamp]

Current status might differ. For real-time status, you can [action]."
```

## Analysis Issues

### Inconclusive Analysis

```markdown
When: Can't reach definitive conclusion

Response Pattern:
"Based on my investigation, I couldn't determine a definitive [conclusion].

Evidence I found:
- [Evidence 1] suggests [possibility A]
- [Evidence 2] suggests [possibility B]

Most likely explanation: [best guess] (confidence: [Low/Medium])

To get more clarity, you could:
- [Suggestion 1]
- [Suggestion 2]"
```

### Contradictory Evidence

```markdown
When: Findings contradict each other

Response Pattern:
"I found contradictory information about [topic]:

- [Source 1] indicates: [finding]
- [Source 2] indicates: [conflicting finding]

Possible explanations:
- [Explanation 1]
- [Explanation 2]

I recommend verifying by [verification step]."
```

## Recovery Patterns

### Graceful Degradation

When a preferred approach fails, fall back to alternatives:

```
1. Primary method fails → Try alternative query
2. Alternative fails → Report partial findings
3. No data available → Explain what can't be analyzed
4. Never leave user without a response
```

### Partial Results

```markdown
When: Some queries succeed, some fail

Response Pattern:
"I completed [X of Y] planned queries.

Successful:
- [Query 1]: [Result]
- [Query 2]: [Result]

Failed:
- [Query 3]: [Error reason]

Based on available data: [what can be concluded]
For complete analysis: [what's missing]"
```

## User Interaction Recovery

### Clarification Limits

```markdown
- Maximum 2 clarifying questions before proceeding with best interpretation
- If still unclear after 2 questions, state assumption and proceed
- Always explain what assumption was made
```

### Stuck State Recovery

```markdown
When: Investigation hits dead end

Response Pattern:
"I've reached the limit of what I can determine through [method].

What I do know:
- [Fact 1]
- [Fact 2]

What remains unknown:
- [Unknown 1]

To proceed, you could:
- [Manual check suggestion]
- [Alternative approach]
- [Ask different question]"
```

# SubAgent Success Metrics

Standard metrics for measuring SubAgent effectiveness.

## Purpose

Success metrics provide:
- Measurable quality targets for agent performance
- User expectations for what "good" looks like
- Feedback mechanism for improvement

## Standard Metrics by Agent Type

### Diagnostic Agents (Troubleshooter)

| Metric | Target | Measurement |
|--------|--------|-------------|
| Diagnosis Accuracy | >85% | Root cause correctly identified |
| First-Contact Resolution | >70% | Issue resolved without follow-up |
| Investigation Time | <5 min | Time to first actionable findings |
| User Clarity | High | Findings understandable without jargon |

### Analysis Agents (Security Audit)

| Metric | Target | Measurement |
|--------|--------|-------------|
| Coverage | >95% | Relevant resources analyzed |
| False Positive Rate | <10% | Issues that aren't actually issues |
| Severity Accuracy | >90% | Correct priority classification |
| Actionability | 100% | Every finding has clear next step |

### Planning Agents (Design Advisor, Change Planner)

| Metric | Target | Measurement |
|--------|--------|-------------|
| Plan Completeness | 100% | All steps included, none missing |
| Rollback Coverage | 100% | Every change has undo path |
| Dependency Accuracy | >95% | Correct order of operations |
| User Confidence | High | User understands and trusts plan |

## Homelab-Appropriate Targets

These metrics are calibrated for homelab environments:
- Lower volume than enterprise (dozens of devices, not thousands)
- Higher tolerance for brief downtime
- User is often the admin and implementer
- Learning and understanding valued alongside fixing

## Measuring Success

Success is ultimately measured by:
1. **Problem Solved**: Did the user achieve their goal?
2. **Understanding Gained**: Does the user understand what happened/will happen?
3. **Confidence Level**: Does the user feel confident proceeding?
4. **Time Efficiency**: Was the interaction respectful of user's time?

## Failure Indicators

Signs the agent is not meeting targets:
- User asks same question again (not understood)
- User reports recommendation didn't work (bad analysis)
- User abandons mid-investigation (too slow/complex)
- User ignores execution plan (doesn't trust it)

# Cross-Agent Integration Patterns

How SubAgents recognize handoff opportunities and collaborate.

## Purpose

SubAgents are specialists. Sometimes an investigation reveals issues in another agent's domain. These patterns define when and how to suggest handoffs.

## Handoff Triggers

### From Troubleshooter

| Finding | Handoff To | Trigger Phrase |
|---------|------------|----------------|
| Architectural problem causing issue | Design Advisor | "This connectivity issue stems from your network architecture. Would you like a design review?" |
| Security misconfiguration found | Security Audit | "I noticed some security concerns while investigating. Want me to do a quick security check?" |
| Complex multi-step fix needed | Change Planner | "The fix requires several coordinated changes. Should I create a detailed migration plan?" |

### From Design Advisor

| Finding | Handoff To | Trigger Phrase |
|---------|------------|----------------|
| Existing security gaps | Security Audit | "Before implementing this design, you may want a security review of your current setup." |
| Complex migration required | Change Planner | "This design change involves migrating existing devices. Want a detailed change plan?" |
| Performance concerns in current setup | Troubleshooter | "I noticed some devices may have connectivity issues. Want me to investigate?" |

### From Security Audit

| Finding | Handoff To | Trigger Phrase |
|---------|------------|----------------|
| Architectural redesign needed | Design Advisor | "Fixing these issues requires restructuring your network. Would you like design consultation?" |
| Complex remediation steps | Change Planner | "The remediation involves multiple steps with dependencies. Want a phased plan?" |
| Device-specific issues found | Troubleshooter | "Some devices show concerning behavior. Want me to investigate specific devices?" |

### From Change Planner

| Finding | Handoff To | Trigger Phrase |
|---------|------------|----------------|
| Design questions during planning | Design Advisor | "This change raises some design questions. Would you like to consult on the architecture first?" |
| Security implications of change | Security Audit | "This change has security implications. Want a security review before proceeding?" |
| Troubleshooting needed post-change | Troubleshooter | "If issues arise after this change, I can help diagnose them." |

## Handoff Format

When suggesting a handoff:

```markdown
---

### Related Investigation

During this [analysis/troubleshooting/planning], I identified an issue that may warrant further investigation:

**Finding:** [What was discovered]
**Domain:** [Design/Security/Troubleshooting/Planning]
**Suggested Action:** [What the other agent would do]

Would you like me to [invoke other agent] to [specific action]?

---
```

## When NOT to Handoff

Don't suggest handoffs when:
- The finding is minor/informational
- It would distract from the user's primary goal
- The user has already indicated scope limits
- You can address it briefly in current context

## Multi-Agent Scenarios

Some requests naturally span multiple agents:

### Scenario: "Help me set up IoT security"

```
1. Design Advisor → Plan IoT VLAN architecture
2. Security Audit → Review security implications
3. Change Planner → Create implementation plan
4. User executes plan
5. Troubleshooter → Available for post-change issues
```

### Scenario: "Why is my network slow and insecure?"

```
1. Troubleshooter → Diagnose performance issues
2. Security Audit → Comprehensive security review
3. Design Advisor → Recommend architectural improvements
4. Change Planner → Create remediation plan
```

### 5.8 User Interaction Guidelines

**File: `.claude/agents/shared/USER-INTERACTION.md`**

```markdown
# User Interaction Guidelines

How SubAgents should interact with users during investigation.

## Clarifying Questions

### When to Ask

Ask clarifying questions when:
- User request is ambiguous
- Multiple interpretations are possible
- Key information is missing
- Scope is unclear

### When NOT to Ask

Don't ask when:
- You can make a reasonable assumption
- The answer won't change your approach
- You've already asked 2 questions
- The question is about implementation details (you're read-only)

### Question Format

```markdown
Good Question Format:
"Before I investigate, I'd like to clarify one thing:
[Specific question]

This will help me [why it matters]."

Bad Question Format:
"I have some questions:
1. [Question]
2. [Question]
3. [Question]
4. [Question]"

Too many questions! Pick the most important 1-2.
```

### Question Types

#### Scope Clarification
```
"Should I analyze [just X] or [also include Y]?"
"Are you interested in [specific aspect] or [broader view]?"
```

#### Identification
```
"I found multiple devices matching 'TV'. Did you mean:
- Living Room TV (Samsung)
- Bedroom TV (LG)"
```

#### Priority
```
"I found several issues. Should I focus on:
- Security concerns (found 3)
- Performance issues (found 2)
- All issues?"
```

## Progress Updates

### When to Update

- Starting investigation: State what you'll do
- Major milestone: "I've gathered network data, now analyzing..."
- Significant finding: "I've discovered something relevant..."
- Completing investigation: Full report

### Update Format

```markdown
Brief Progress:
"Investigating... I've queried the device and found it's wireless.
Now checking AP status and signal quality."

Not:
"I am now going to use the unifi_get_client tool to query the device
information. Then I will check the unifi_get_device tool to get the
access point information. Following that..."

Too verbose! Be concise.
```

## Presenting Findings

### Structure

1. **Lead with the answer/conclusion**
2. Provide supporting evidence
3. Note confidence level
4. Offer deeper details if wanted

### Example

```markdown
Good:
"Your TV is disconnecting due to weak WiFi signal (-72 dBm).
It's connected to the far AP when a closer one exists.

Evidence:
- Signal strength is in 'Poor' range
- Living Room AP is 20 feet closer
- No roaming events in past 24 hours

Recommendation: [solution]"

Not:
"I queried the device and found MAC aa:bb:cc:dd:ee:ff with IP
192.168.1.45 connected to AP with MAC 11:22:33:44:55:66 which
is named 'Basement AP' and the signal is -72 dBm and the channel
is 36 and..."

Information overload! Synthesize first, detail later.
```

## Offering Next Steps

### Always End With Clear Options

```markdown
"Based on this analysis, you can:
1. [Option 1] - I can provide an execution plan
2. [Option 2] - I can investigate further
3. [Option 3] - No action needed

What would you like to do?"
```

### For Changes

```markdown
"To implement this recommendation:
1. Review the Execution Plan below
2. Run each command when ready
3. Ask me if any step is unclear

[Execution Plan]"
```
