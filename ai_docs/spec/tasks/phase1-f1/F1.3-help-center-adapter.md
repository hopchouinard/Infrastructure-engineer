## 4. Design Decisions

### 4.1 Playwright Integration for Cloudflare Bypass

**Problem:** The Help Center (help.ui.com) uses Cloudflare protection that returns 403 responses to simple HTTP requests. This blocked all scraping attempts using the standard `Fetcher`.

**Decision:** Implement `BrowserFetcher` using Playwright to handle JavaScript challenges.

**Why This Approach:**
1. Cloudflare's JS challenge requires a real browser to execute JavaScript
2. Simple header manipulation or session cookies are insufficient
3. Playwright provides reliable, headless browser automation
4. The `BrowserFetcher` implements the same interface as `Fetcher`, enabling polymorphism

**Trade-offs:**
- (+) Works reliably against Cloudflare protection
- (+) Can handle any JS-based anti-bot measures
- (-) Slower than direct HTTP requests (~2-3s per page vs ~100ms)
- (-) Higher resource usage (browser process)
- (-) Requires `playwright install chromium` setup step

**Files Created:**
- `src/doc_crawler/browser.py` - BrowserFetcher class

### 4.2 FetcherProtocol Interface

**Problem:** The HelpCenterAdapter needed to work with either `Fetcher` (HTTP) or `BrowserFetcher` (Playwright).

**Decision:** Add `FetcherProtocol` to `fetcher.py` using Python's `typing.Protocol`.

**Why This Approach:**
1. Enables adapter to accept either fetcher type without tight coupling
2. Protocol is `@runtime_checkable` for duck typing
3. No changes required to existing `Fetcher` class behavior

**Change to Settled Work:** This was an *addition* to F1.2, not a modification. The existing `Fetcher` class was unchanged.

### 4.3 CSS Selector Fallbacks

**Problem:** Zendesk templates can vary, and the Help Center's HTML structure had changed since the spec was written.

**Decision:** Use ordered lists of CSS selectors with fallback behavior.

**Why This Approach:**
1. Most specific selectors first for accuracy
2. Less specific fallbacks for resilience
3. Avoids overly broad selectors that could match unintended elements
4. Warnings logged when fallbacks are used

**Current Selectors (Updated 2024):**
```python
SECTION_SELECTORS = [
    "a.latest_articles__show-more[href*='/sections/']",  # Current primary
    "section.section .section-tree-title a",              # Legacy fallback
    ".section-tree-title a",
    ".category-sections a[href*='/sections/']",
    ".section a[href*='/sections/']",
]

ARTICLE_LIST_SELECTORS = [
    "a.section-article__list-name[href*='/articles/']",  # Current primary
    ".section-item__article a[href*='/articles/']",
    ".article-list-item a",                               # Legacy fallback
    "ul.article-list a",
    ".article-list a[href*='/articles/']",
]
```

### 4.4 Section Name Extraction from URL Slug

**Problem:** The current Help Center template shows "View all X" as link text instead of section names.

**Decision:** Extract section names from URL slugs when link text is not meaningful.

**Why This Approach:**
1. URL slugs contain the human-readable section name (e.g., `Getting-Started-with-UniFi`)
2. Fallback logic: use link text if meaningful, otherwise parse URL slug
3. Converts slug format to title case (e.g., "Getting Started With Unifi")

### 4.5 Semantic Path Generation as Standalone Functions

**Problem:** The spec suggested adding `generate_output_path()` to `CrawlItem`, but this creates coupling.

**Decision:** Keep path generation as standalone functions in `paths.py`.

**Why This Approach:**
1. Single Responsibility: CrawlItem handles crawl metadata, paths.py handles path generation
2. Easier to test independently
3. Can be used without a CrawlItem instance
4. Original article_id preserved in frontmatter for traceability

### 4.6 Word Boundary Matching for Topic Classification

**Problem:** Substring matching caused false positives (e.g., "port" matching in "teleport").

**Decision:** Use regex word boundaries (`\b`) for keyword matching.

**Why This Approach:**
1. Prevents partial word matches
2. More accurate topic classification
3. Works correctly with multi-word keywords

## 9. Usage Examples

### 9.1 Basic Usage with BrowserFetcher

```python
import asyncio
from doc_crawler.browser import BrowserFetcher, BrowserFetcherConfig
from doc_crawler.config import CrawlerConfig
from doc_crawler.adapters.help_center import HelpCenterAdapter

async def main():
    config = CrawlerConfig()
    config.rate_limit.requests_per_second = 0.5  # Slower for browser

    browser_config = BrowserFetcherConfig(
        headless=True,
        timeout=60000,
        cloudflare_timeout=20.0,
    )

    async with BrowserFetcher(config, browser_config) as fetcher:
        adapter = HelpCenterAdapter(config.sources.help_center, fetcher)

        async for item in adapter.discover():
            print(f"Found: {item.get_metadata().get('title')}")

asyncio.run(main())
```

## 10. Known Limitations

1. **Rate Limiting:** BrowserFetcher is inherently slower (~2-3s per page). Integration tests take ~17s for 5 pages.

2. **Selector Fragility:** HTML selectors may break if Zendesk updates their templates. The fallback system mitigates this but doesn't eliminate the risk.

3. **No robots.txt Support in BrowserFetcher:** By design, BrowserFetcher doesn't check robots.txt since it's specifically for bypassing protection on sites we've determined we want to access.

4. **Browser Installation Required:** Users must run `playwright install chromium` before using BrowserFetcher.
