### 4.1 Configuration Changes

```python
class RateLimitConfig(BaseModel):
    """Rate limiting and timeout configuration."""

    requests_per_second: Annotated[float, Field(gt=0, le=100)] = 1.0
    respect_robots_txt: bool = True
    request_timeout: Annotated[float, Field(gt=0, le=300)] = 30.0
    robots_timeout: Annotated[float, Field(gt=0, le=60)] = 10.0
```

### 4.2 FetchResult Dataclass

```python
@dataclass
class FetchResult:
    """Result of a fetch operation."""
    url: str
    status_code: int
    content: bytes
    content_type: str
    headers: dict[str, str]
    success: bool
    error: str | None = None
    elapsed_ms: float = 0.0
```

### 4.3 RateLimiter Class

Token bucket rate limiter with:
- Configurable requests per second
- Async lock for thread safety
- First request is immediate (no initial wait)

### 4.4 RobotsChecker Class

robots.txt compliance checker with:
- Per-domain caching
- Configurable timeout
- Graceful handling of missing/inaccessible robots.txt (allows all)
- Narrow exception handling (httpx-specific exceptions only)

### 4.5 Fetcher Class

Main HTTP fetcher with:
- Async context manager pattern
- Rate limiting on all requests
- robots.txt compliance (configurable)
- Retry logic with exponential backoff
- Configurable timeouts from config

### 4.6 Rate Limiter Details

The rate limiter:
1. Uses token bucket algorithm (simplified)
2. Is thread-safe (uses asyncio.Lock)
3. Supports configurable requests per second
4. Works correctly with concurrent requests
5. First request is immediate (no artificial delay)

### 4.7 Robots.txt Handling

The robots checker:
1. Caches robots.txt per domain
2. Handles missing robots.txt gracefully (allow all)
3. Handles fetch errors gracefully (allow all)
4. Uses the configured User-Agent string
5. Uses configurable timeout for fetching

### 4.8 Retry Logic

Retry behavior:
1. Retry on 5xx server errors
2. Retry on 429 rate limit responses (counts against max_retries)
3. Retry on timeout
4. Retry on connection errors
5. Do NOT retry on 4xx client errors (except 429)
6. Use exponential backoff (1s, 2s, 4s, ...)
7. Respect server's Retry-After header on 429

## 9. Design Decisions

This section documents the key design decisions made during implementation and the reasoning behind each choice.

### 9.1 Mutable FetchResult Dataclass

**Decision:** Use regular `@dataclass` (mutable) for `FetchResult`, not frozen.

**Why:**
- **Short-lived objects**: `FetchResult` is created, used immediately, and discarded. It doesn't pass through multiple pipeline stages like `CrawlResult`.
- **No thread-safety concerns**: Results are not shared between coroutines.
- **Simpler code**: No need for tuple metadata or factory methods.

**Contrast with F1.1:** `CrawlItem` and `CrawlResult` are frozen because they pass through the crawl pipeline and need immutability for thread safety.

### 9.2 Export All Classes

**Decision:** Export all four classes (`Fetcher`, `FetchResult`, `RateLimiter`, `RobotsChecker`) in `__all__`.

**Why:**
- **Testing flexibility**: Tests can import `RateLimiter` directly for isolated unit tests.
- **Reusability**: `RateLimiter` is generic enough for other use cases.
- **Internal project**: No external API stability concerns since this is an internal tool.

### 9.3 Configurable Timeouts

**Decision:** Add `request_timeout` and `robots_timeout` to `RateLimitConfig` instead of hardcoding.

**Why:**
- **Flexibility**: Different network conditions may require different timeouts.
- **Testing**: Allows faster timeouts in tests.
- **Consistency**: Follows the pattern of making behavior configurable.

**Trade-off:** Slightly more complex config, but the flexibility is worth it.

### 9.4 First Request Immediate

**Decision:** Initialize `RateLimiter._last_request` to 0 instead of `time.monotonic()`.

**Why:**
- **User expectation**: First request should be immediate, not wait for rate limit.
- **Performance**: Avoids unnecessary delay at startup.
- **Bug fix**: Original spec had this issue where first request would wait.

### 9.5 429 Counts Against Retries

**Decision:** Count 429 (rate limited) responses against `max_retries`.

**Why:**
- **Safety**: Prevents infinite loop if server keeps returning 429.
- **Predictability**: User knows exactly how many attempts will be made.
- **Original spec issue**: The spec didn't count 429 against retries, which could cause hangs.

### 9.6 HEAD Has Full Retry and Robots Support

**Decision:** Give `head()` the same retry logic and robots.txt checking as `get()`.

**Why:**
- **Consistency**: Both methods should behave similarly.
- **Safety**: HEAD requests should also respect robots.txt.
- **Robustness**: HEAD requests can also fail transiently.

**Original spec:** `head()` had no retry or robots.txt support, which was inconsistent.

### 9.7 Narrow Exception Handling in RobotsChecker

**Decision:** Catch `(httpx.RequestError, httpx.TimeoutException)` instead of `Exception`.

**Why:**
- **Debugging**: Broad `except Exception` masks unexpected errors.
- **Safety**: Still allows all requests if robots.txt can't be fetched.
- **Best practice**: Catch specific exceptions when possible.

### 9.8 User-Agent String

**Decision:** Use `UniFi-Doc-Crawler/1.0 (+https://github.com/hopchouinard/Infrastructure-engineer)`.

**Why:**
- **Identification**: Allows site operators to identify the crawler.
- **Traceability**: URL points to project repository.
- **Best practice**: Well-behaved crawlers identify themselves.

### 9.9 Explicit Parameters Instead of **kwargs

**Decision:** Use explicit `max_retries` and `retry_delay` parameters in `get_text()` instead of `**kwargs`.

**Why:**
- **Type safety**: Proper type hints instead of `**kwargs: int | float`.
- **IDE support**: Better autocomplete and documentation.
- **No type: ignore comments**: Cleaner code without suppression comments.

### CR-001: Add Timeout Configuration

**Change:** Added `request_timeout` and `robots_timeout` to `RateLimitConfig`.

**Reason:** User requested configurable timeouts for flexibility (Q3.B during pre-implementation questions).

**Approved:** Yes, during initial Q&A.

### CR-002: Export All Classes

**Original Spec:** Not specified.

**Change:** Export `Fetcher`, `FetchResult`, `RateLimiter`, `RobotsChecker` in `__all__`.

**Reason:** User approved exporting all classes for testing flexibility (Q5.B during pre-implementation questions).

**Approved:** Yes, during initial Q&A.

### CR-003: Fix 429 Infinite Loop

**Original Spec:** 429 responses did not count against `max_retries`.

**Change:** 429 now counts against retries, returns error when exhausted.

**Reason:** Code review identified potential infinite loop if server keeps returning 429.

**Approved:** Yes, during code review.

### CR-004: Add Retry and Robots to HEAD

**Original Spec:** `head()` had no retry logic or robots.txt checking.

**Change:** `head()` now has full retry logic and checks robots.txt.

**Reason:** Code review identified inconsistency with `get()` behavior.

**Approved:** Yes, during code review.

### CR-005: Narrow Exception Handling

**Original Spec:** `except Exception` in RobotsChecker.

**Change:** `except (httpx.RequestError, httpx.TimeoutException)`.

**Reason:** Code review identified that broad exception catch could mask errors.

**Approved:** Yes, during code review.

### CR-006: Explicit Parameters in get_text

**Original Spec:** `**kwargs: int | float` with type ignore comment.

**Change:** Explicit `max_retries` and `retry_delay` parameters.

**Reason:** Code review identified imprecise type hints.

**Approved:** Yes, during code review.

### CR-007: First Request Immediate

**Original Spec:** `_last_request = field(default_factory=time.monotonic)`.

**Change:** `_last_request = field(default=0.0)`.

**Reason:** Test failure showed first request waited for full rate limit interval.

**Approved:** Yes, as bug fix during testing.
